  - v18: PTW에 이미 `등록→위험확인중→승인대기→승인됨→작업중→종료` 승인 워크플로우가 존재.

- **AI 기능은 Anthropic이 아니라 Google Gemini(`gemini-flash-latest`)**입니다. `AI_KEY_STORAGE`라는 별도 localStorage 키에 API 키를 저장하고 `x-goog-api-key` 헤더로 브라우저에서 직접 `generativelanguage.googleapis.com`을 호출합니다. 위험성평가 초안/TBM 스크립트/5-Why 원인분석/월간보고서 초안 4개 모드가 이미 구현되어 있고, 흥미롭게도 코드 주석에 "2026-08-27 사용자 피드백"으로 월간보고서 모드의 토큰 한도를 늘렸다는 기록이 있습니다 — 오늘 직접 고치신 부분이죠. 이 키는 백업 파일에는 포함되지 않도록 이미 분리되어 있어 그 부분은 안전하지만, **"브라우저에서 벤더 API로 직접 호출"** 구조 자체는 지시서 30/47번이 지적한 문제 그대로입니다.
- **서버 전환에 유리한 기존 설계를 발견했습니다.** `SafetyRepository`(v13 도입)의 코드 주석에 이렇게 적혀 있습니다: *"지금은 안에서 State.safetyData(=localStorage)를 그대로 쓰지만, 나중에 실제 서버가 생기면 이 5개 함수 내부만 fetch() 호출로 바꾸면 되고 호출부는 그대로 재사용됩니다."* — 정확히 저희가 하려는 작업을 이미 예상하고 만들어 둔 추상화입니다. 다만 주석에 따르면 **CAPA만 이 계층을 거치고, 나머지 13개 모듈은 여전히 State.safetyData를 직접 참조**합니다. 서버 전환 시 이 13개 모듈에도 같은 리팩터링을 먼저 적용하는 게 안전합니다.
- **이미 구현된, 지시서가 "추가하라"고 한 기능들**: `DeadlineEngine`(기한 D-day 계산 공통 엔진, CAPA/건강진단/법정선임/PPE가 공유), `RepeatDetectionEngine`(반복위험 감지 — 17번 항목), `ContractorEngine`(협력업체 전용 엔진 — 13번 항목), `BulkOps`(일괄처리 — 42번 항목), 반기/연간 법정 일정 자동 생성(43번 항목의 축소판). **즉 이번 작업의 실체는 "없는 로직을 새로 짜는 것"이 아니라 "이미 맞게 짜여 있는 로직을 서버·다중 사용자 기반으로 옮기는 것"에 더 가깝습니다.**
- 서브탭 구성(`SAFETY_MENU_ITEMS`): 대시보드·CAPA·위험성평가·사고관리·MSDS·건강진단·PTW·안전교육·TBM·법정선임·법정회의점검·PPE·협력업체·아차사고·안전의 소리함·AI 비서·통합검색·통계 (18개, 사용자가 순서 편집 가능) — 여기에 오늘의 업무/주간일지/월간보고/백업복원/감사로그가 별도 영역으로 존재합니다.
- **백업/복원**: `Actions.exportBackupJSON()` / `Actions.importBackupJSON()` / `Actions.confirmRestoreDefaults()`. 앱 UI에 "백업/내보내기 파일에는 AI 키가 포함되지 않습니다"라는 안내 문구가 이미 있을 만큼 이 부분은 신경 써서 설계되어 있습니다.

## 3. 배포 준비 (오늘 작업)

**오늘 우선순위로 정하신 게 이 부분입니다.** 인터넷에 상시 떠 있는 서버 자체는 사용자의
호스팅 계정이 있어야만 실제로 생기지만, "계정만 있으면 바로 되는" 상태까지는 오늘
전부 만들고 로컬에서 검증했습니다.

### 3-1. 보안/설정 (검증됨)

- **JWT_SECRET 강제**: `NODE_ENV=production`인데 `JWT_SECRET`이 없으면 서버가 **기동 자체를
  거부**합니다. 예전엔 개발용 기본값(`dev-only-secret-change-me-before-deploy`)으로 조용히
  넘어갔는데, 이게 운영에서 진짜 보안 사고로 이어질 수 있어서 막았습니다. 실제로
  `NODE_ENV=production node server.js`를 JWT_SECRET 없이 실행해서 크래시하는 것과,
  설정 후 정상 기동하는 것 둘 다 확인했습니다.
- **CORS**: PWA가 API와 다른 도메인(예: Netlify)에 있을 수 있으므로 `CORS_ORIGIN` 환경변수로
  허용 출처를 지정합니다. 운영 모드(`NODE_ENV=production`)에서 비워두면 `JWT_SECRET`과
  동일하게 기동 자체를 거부합니다(2026-08-28 강화 — 예전엔 경고만 남기고 전체 허용했음).
- **환경변수 정리**: `.env.example` 참고. `JWT_SECRET`, `NODE_ENV`, `PORT`, `CORS_ORIGIN`,
  `DB_PATH` 다섯 가지입니다.
- **자동 시드**: 서버가 처음 뜰 때 `ensureSeed()`가 자동 실행되어 역할/권한 체계가 준비됩니다.
  2026-08-30(SaaS 전환)부터는 특정 조직(옛 "DB그룹-DB월드")을 자동으로 만들지 않습니다 —
  조직은 이제 `/setup` 화면(브라우저에서 회사명/관리자 계정 입력) 또는 `POST /organizations`
  API를 통한 실제 가입으로만 생깁니다. 역할/권한 시딩은 이미 있으면 아무것도 안 하므로
  재배포해도 안전합니다(멱등).
- **Graceful shutdown**: 컨테이너 플랫폼은 재배포·스케일 조정 시 `SIGTERM`을 보냅니다.
  진행 중인 요청을 마무리하고 DB 핸들을 정리한 뒤 종료하도록 만들었고, 실제로 SIGTERM을
  보내 프로세스가 깨끗이 종료되는 것까지 확인했습니다.
- **요청 로그**: 배포 직후 트래픽이 실제로 들어오는지 바로 눈으로 볼 수 있는 최소 로그를
  추가했습니다 (`시각 METHOD /경로` 형식).

### 3-2. Docker

`Dockerfile`을 만들었습니다. `node:22-slim`(glibc) 베이스를 썼는데, `better-sqlite3`가
플랫폼별 프리빌드 바이너리를 받는 방식이라 alpine(musl)으로 하면 소스 컴파일이 필요해질 수
있어 피했습니다. **다만 이 샌드박스 자체에 Docker가 없어서 `docker build`로 실제 이미지를
빌드해보는 것까지는 못 했습니다** — 문법과 로직은 확인했지만, 받으신 후 로컬에서
`docker build -t safety-meerkat-server .` 로 한 번 직접 빌드해보시길 권장합니다.

SQLite 파일은 컨테이너 안 `/app/data/data.sqlite`에 저장되도록 했습니다. 컨테이너 자체는
재배포마다 새로 만들어지는 게 정상이므로, **이 경로에 플랫폼의 영구 볼륨을 반드시
마운트해야** 재배포 후에도 데이터가 남습니다 (아래 3-3 참고).

### 3-3. 배포 플랫폼 — Railway (권장, 절차 확인됨)

Railway의 볼륨 동작 방식을 실제 공식 문서로 확인하고 정리한 순서입니다:

1. GitHub에 이 저장소를 올린다 (`.gitignore`에 `node_modules`/`.env`/`data.sqlite`가
   이미 제외되어 있습니다).
2. Railway에서 "New Project → Deploy from GitHub repo"로 이 저장소를 연결한다.
   `Dockerfile`이 있으므로 Railway가 자동으로 감지해서 빌드합니다.
3. 서비스에 **Volume**을 하나 붙인다 (예: 마운트 경로 `/app/data`). Railway는 볼륨을 붙이면
   `RAILWAY_VOLUME_MOUNT_PATH` 환경변수를 자동으로 주입해줍니다.
4. Variables 탭에서 환경변수를 설정한다:
   - `JWT_SECRET` = (직접 생성한 랜덤 값)
   - `NODE_ENV` = `production`
   - `CORS_ORIGIN` = PWA가 서빙되는 도메인
   - `DB_PATH` = `/app/data/data.sqlite` (3번에서 마운트한 경로 밑)
5. Networking에서 공개 도메인을 생성한다.

**주의**: Railway 공식 문서에 "볼륨은 빌드 단계에서는 사용할 수 없고 런타임에만 붙는다"고
명시되어 있습니다. 저희 코드는 SQLite 파일을 서버가 실제로 뜰 때(런타임)만 열기 때문에
문제없지만, 혹시 나중에 빌드 단계에서 DB 파일을 미리 만드는 식으로 바꾸면 이 부분에서
막힐 수 있다는 점을 기억해두시면 좋습니다.

### 3-4. 대안 — Fly.io

`fly.toml.example` 파일을 참고용으로 만들어뒀습니다만, **이 샌드박스에 Fly CLI/계정이 없어
실제 배포 테스트는 못 했습니다.** 정확한 최신 문법이 바뀌었을 수 있으니, 그대로 쓰기보다는:

```bash
fly launch   # Dockerfile을 자동 감지해서 최신 형식의 fly.toml을 직접 생성해줍니다
fly volumes create safety_meerkat_data --size 1
fly secrets set JWT_SECRET=$(node -e "console.log(require('crypto').randomBytes(48).toString('hex'))")
```
로 진행하시고, `fly.toml.example`의 `[[mounts]]`/`[http_service.checks]` 부분만 생성된

### 3-5. Render 등 다른 플랫폼

Render도 Persistent Disk 기능으로 같은 패턴(볼륨 마운트 + 환경변수)이 가능합니다. Dockerfile
기반이라 어떤 컨테이너 플랫폼을 쓰든 원리는 동일합니다 — "영구 볼륨 마운트 경로 = DB_PATH가
가리키는 위치"만 맞추면 됩니다.

## 5. 오늘 실행한 검증 시나리오

1. 안전관리자·근로자 계정을 각각 등록하고 로그인 → 서로 다른 JWT, 서로 다른 권한 확인
2. 근로자가 가능성5×중대성4=20점짜리 고위험 위험성평가 등록 → CAPA(`CAPA-2026-000001`) 자동 생성 확인
3. 근로자가 그 항목을 완전삭제 시도 → **403** (risk.delete_any 없음), 안전관리자는 정상 처리
4. CAPA를 "등록→완료요청"으로 건너뛰려는 시도 → **422** 차단, "등록→조치중"은 정상 처리

   → **처음 실행에서 0건이 이관되는 버그를 실제로 발견했습니다.** `created_by NOT NULL` 제약과
   `INSERT OR IGNORE`가 만나 제약 위반 행을 조용히 건너뛰고 있었습니다(예외가 안 나서 로그만
   보면 "성공"처럼 보였습니다). `created_by`를 NULL 허용으로 바꾼 뒤 재검증 — 구형 id는 새
   `RISK-2026-000002`로 채번되며 `legacy_id='r1'`을 보존했고, 신형 id는 그대로 유지되며
   카운터가 충돌 없이 5까지 올라간 것을 확인했습니다.
7. **(배포 준비) `NODE_ENV=production` + `JWT_SECRET` 미설정** → 서버가 즉시 크래시하며 명확한
   한국어 오류 메시지 출력 확인. `JWT_SECRET` 설정 후에는 정상 기동 확인.
8. **(배포 준비) `NODE_ENV=production` + 모든 환경변수 설정** 상태로 `/health` 호출 →

9. **(배포 준비) SIGTERM 전송** → "graceful shutdown 시작" 로그 → 프로세스가 실제로

10. **(배포 준비) `node_modules` 삭제 후 `npm install`부터 전체 재현** — 받는 사람 입장에서

## 11. 참고: 왜 지금 PostgreSQL로 안 옮겼는가

지난 세션 README에는 "운영은 PostgreSQL 권장"이라고 적었지만, 오늘 실제로 방향을
바꿨습니다. 이유는 두 가지입니다.

1. **위험 대비 이득이 낮습니다.** better-sqlite3(동기)에서 pg(비동기)로 옮기려면 모든 라우트/
   `ids.js`/`audit.js`/`seed.js`/마이그레이션 스크립트를 한 번에 async로 다시 써야 하는데,
   지시서 27번 원칙("문제가 생기면 임시방편보다 원인 해결")과 이 프로젝트가 계속 강조해온
   "고치면 반드시 재검증" 원칙을 지키려면 이 리라이트 전체를 오늘 다시 테스트해야 합니다.
   지금 이 사용자 규모(계정 소수)에서는 그 위험을 감수할 실익이 없다고 판단했습니다.
2. **SQLite가 이 규모에서 운영 부적합하지 않습니다.** Railway/Fly 모두 "볼륨에 SQLite"를
   공식적으로 지원하는 패턴으로 문서화하고 있고(3-3절), 계정 수가 실제로 늘어 동시 쓰기가
   병목이 될 때 PostgreSQL로 옮기는 게 지금 미리 옮기는 것보다 오히려 안전합니다(지시서
   14번 "성능 최적화는 실제 병목을 확인한 후 적용" 원칙과도 맞습니다).

`better-sqlite3`는 프리빌드 바이너리를 받아오는 패키지라 환경에 따라 설치가 실패할 수
있습니다. 이번 세션에서는 정상 설치됐지만, 다른 환경에서 안 될 경우 `sql.js`(순수 JS/WASM,
항상 설치됨)로 `src/db.js` 한 파일만 바꾸면 됩니다.

나중에 PostgreSQL로 옮길 때를 대비해 지금부터 지켜두면 좋은 것: 쿼리는 지금처럼 각 라우트
안에 짧게 유지하고(레포지토리 패턴으로 과도하게 추상화하지 않음), `?` 포지셔널 파라미터
스타일을 유지하면 `pg`의 `$1,$2`로 바꿀 때 SQL 문자열 자체의 구조는 거의 그대로 재사용할 수
있습니다.

## 12. 프론트엔드 실연동 (v5.9)

**이 저장소와 별개인 프론트엔드 파일**(`안전미어캣프로_v5_9_서버연동.html`, 이전 세션에서
9개 PWA 확장모듈까지 병합된 v5.8을 기반으로 함)이 이 서버에 실제로 연결됩니다.

### 12-1. 무엇이 연결됐는가

- **로그인**: 설정 탭에 "서버 연결" 섹션 추가. 서버 주소 입력 → `POST /auth/login` 호출 →
  JWT를 이 브라우저의 별도 localStorage 키에 저장(AI 키와 동일한 격리 패턴, 백업파일에는
  포함 안 됨). 401 응답 시 자동 로그아웃 처리.
- **위험성평가 신규 등록**: 기존처럼 항상 로컬(localStorage)에 즉시 저장되고, **추가로**
  서버가 연결·로그인되어 있으면 `SyncQueue`(지난 세션에 병합된 오프라인 큐)에 등록되어
  온라인 상태면 즉시, 오프라인이었다면 재연결 시 자동으로 서버에 전송됩니다.
- **서버 목록 조회**: 설정 탭에 "서버에 등록된 위험성평가 보기" 버튼 — 같은 사업장의
  다른 사용자가 등록한 항목도 조회됩니다. **의도적으로 로컬 목록과 분리해서 보여줍니다**
  (자동 병합/중복제거는 다음 단계, 아래 12-3 참고).
- 서버 연결은 **완전히 선택사항**입니다. 주소를 설정하지 않으면 이전과 동일하게 100%
  로컬 전용으로 동작하며, 기존 사용자 경험은 전혀 바뀌지 않습니다.

### 12-2. 서버 쪽에 있었던 실제 문제와 수정

프론트엔드를 연결해보면서 이 서버 코드 자체에 있던 문제 하나를 발견해 고쳤습니다:

- **문제**: 프론트엔드는 이미 `IdGenerator`로 `RISK-2026-000042` 같은 완성된 id를 로컬에서
  채번해 쓰고 있는데, 서버의 `POST /risks`는 항상 자기 카운터로 **새 id를 또** 채번했습니다.
  그러면 같은 레코드가 로컬에서는 000042, 서버에서는 000001처럼 서로 다른 id를 갖게 되어
  나중에 로컬↔서버 데이터를 id로 대조할 방법이 없어집니다.
- **수정**: `resolveClientOrNewId()`(`src/ids.js`)를 추가해, 클라이언트가 이미 올바른 형식의
  id를 보내면 그대로 신뢰해서 쓰고(카운터만 그 번호 이상으로 맞춰 올림), 없거나 형식이
  안 맞으면 그때만 서버가 새로 채번하도록 바꿨습니다.
- **부수적으로 발견한 문제**: `SyncQueue`는 실패 시 재시도하는 구조라, 같은 id로 서버에
  두 번 POST될 수 있습니다(예: 서버는 저장했는데 응답 도중 연결이 끊긴 경우). 기존 코드라면
  `id TEXT PRIMARY KEY` 제약 위반으로 500 에러가 났을 것입니다 — **재시도가 안전하지
  않은 상태**였던 것입니다. 이미 존재하는 id로 POST가 오면 에러 대신 `alreadyExisted: true`와
  함께 200을 반환하도록 고쳐서, 재시도해도 중복 생성되지 않게(멱등하게) 만들었습니다.
- 이 두 가지 모두 raw HTTP 요청으로 직접 재현해 수정 전/후 동작을 확인했습니다(아래 12-4).

### 12-3. 의도적으로 하지 않은 것 (다음 단계)

- **서버→로컬 자동 병합**: 지금은 "서버 목록 보기"가 로컬 목록과 별개의 읽기 전용 화면입니다.
  같은 화면에 통합해서 보여주려면 로컬 id와 서버 id가 겹치는 경우/안 겹치는 경우를 구분하는
  병합 로직이 필요한데, 잘못 만들면 항목이 중복되거나 사라져 보이는 위험이 있어 이번 범위에서
  뺐습니다.
- **CAPA 프론트엔드 연동**: 서버 API(`GET /capa`, `PATCH /capa/:id/status`)는 지난 세션에
  이미 있지만, 프론트엔드 쪽 연결은 이번에 risk만 했습니다. 패턴은 동일해서 빠르게 확장
  가능합니다.
- **위험성평가 수정/삭제 동기화**: 서버 API 자체가 아직 생성/조회/삭제만 있고 수정(PATCH)이
  없어서, 프론트엔드에서 기존 항목을 수정해도 서버에는 반영되지 않습니다(신규 등록만 정직하게
  연동).

### 12-4. 검증 방법과 결과

raw HTTP 요청으로 서버 로직만 검증한 것과, **실제 앱 화면(jsdom)에서 로그인부터 등록까지
전체 플로우를 검증한 것** 두 단계로 확인했습니다.

```
1) 클라이언트 제공 id로 POST          → 201, 그 id 그대로 저장됨
2) 완전히 동일한 요청 재전송(재시도 시뮬레이션) → 200, alreadyExisted: true (중복 생성 안 됨)
3) id 없이 새 항목 POST               → 201, 카운터가 충돌 없이 다음 번호로 이어짐

4) (프론트엔드 화면에서) 서버 미연결 상태 진입 → "서버가 연결되지 않았습니다"
5) 서버 주소 저장                     → "로그인하지 않았습니다"
6) 로그인 폼 제출                     → "OOO님으로 로그인됨" (실제 서버가 발급한 세션)
7) 위험성평가 등록(실제 폼 입력 → 저장) → 로컬에 즉시 저장 + 서버에도 실제로 반영됨을
                                        서버 API 재조회로 직접 확인
8) 전 과정 동안 JS 에러 0건
```

이 샌드박스엔 실제 브라우저가 없어 jsdom(가상 DOM + 실제 Node fetch)으로 검증했습니다.
실제 모바일 브라우저에서의 최종 확인은 아직 못 했습니다.

## 15. 마지막 3개 모듈 연동 (v5.13) — 법정선임·협력업체·PTW

이제 안전관리 13개 모듈 중 **13개 전부**가 서버와 연결됩니다. 법정선임·협력업체는 기존
공용 생성기를 재사용했고, PTW는 CAPA와 동일하게 서버가 승인 워크플로우를 강제하는
전용 라우트로 만들었습니다.

### 15-1. PTW 상태전이 — 프론트엔드에 명시적으로 없던 부분은 CAPA 패턴을 참고해 설계

프론트엔드의 `PTW_NEXT_STATUS`는 정상 진행 경로(등록→위험확인중→...→종료)만 정의되어
있고, "반려"가 어느 단계에서 가능한지는 코드에 명시되어 있지 않았습니다. CAPA의
반려 패턴(검증중→반려→조치중 재작업)을 참고해 **위험확인중/승인대기 단계에서 반려 가능,
반려되면 등록 단계로 돌아가 재작업**하는 것으로 합리적으로 설계했습니다. **이 부분은 추측이
섞여 있습니다** — 실제 사용해보시고 다르게 동작해야 한다면 `src/routes/ptw.js`의
`PTW_TRANSITIONS`만 고치면 됩니다.

승인(`승인대기→승인됨`)은 CAPA의 `capa.approve`와 동일하게 `ptw.approve` 권한 보유자만
가능하도록 했고, 상태가 바뀔 때마다 `approved_at`/`work_started_at`/`closed_at`
타임스탬프를 자동 기록합니다.

### 15-2. 검증 중 실제로 잡은 문제 (또 발견한 "select인데 자유텍스트로 착각" 패턴)

이번에도 테스트 스크립트가 처음엔 법정선임 등록에 실패했습니다. `f-appoint-role`(직책)이
`<select>`인데 임의 문자열을 넣어 실제로는 빈 값으로 처리된 것이었습니다(14절에서 PPE의
`f-ppe-type`에 있었던 것과 동일한 종류의 실수). 실제 옵션값(`보건관리자` 등)으로 고쳐서
재검증했습니다. 두 번 연속 같은 유형의 문제를 만났다는 것은, 프론트엔드에 `<select>`로
되어 있는 필드가 여러 곳 있고 자동화 스크립트를 짤 때 반드시 확인해야 한다는 뜻이라
여기 명확히 기록해둡니다.

```

          감독자가 단계 건너뛰기 시도(422) → 감독자가 정상 진행 2단계(200,200) →

프론트:   실제 화면에서 법정선임/협력업체 등록 → 서버 반영 확인
```

## 17. 협력업체 실제 연동 (v5.14)

15절에서 남겨뒀던 항목입니다 — 위험성평가·사고관리·아차사고·TBM·안전교육·법정회의점검·PTW

않았습니다.

### 17-1. 설계: 로컬과 동일하게 "회사명 문자열"로 연동

로컬 앱을 읽어보니 이미 협력업체를 참조하는 방식이 정해져 있었습니다 — 별도의 외래키가
아니라 **업체명 문자열**로 연동하고 있었습니다(`f-linked-contractor` select가
`State.safetyData.contractor`의 `companyName`을 옵션으로 나열). 새로운 관계형 스키마를
설계하는 대신 이미 있는 방식을 서버에도 그대로 반영했습니다 — 7개 테이블에
`related_contractor TEXT` 컬럼을 추가하고, 각 라우트가 이 필드를 받아 저장하도록 했습니다.

### 17-2. 검증 결과

로컬에서 협력업체를 새로 등록 → 위험성평가 등록 화면을 열어 방금 등록한 업체가 드롭다운에
실제로 뜨는지 확인 → 그 업체를 선택하고 저장 → 서버에 정확히 그 업체명이 `related_contractor`
컬럼에 반영됐는지 재조회로 확인. 전체 흐름이 한 번에 통과했습니다.

이 검증은 이제 `frontend-tests` 패키지의 정식 테스트 항목(4-1번)으로 포함되어 있어,
앞으로 이 부분을 건드릴 때도 자동으로 회귀를 잡아낼 수 있습니다. 협력업체 연동 검증까지
포함해 전체 **35개 항목 전부 통과**를 재확인했습니다.

## 18. 관제센터 — 웹 관리자 대시보드 (신규, 별도 배포 — admin-dashboard.zip)

지금까지 모바일 앱과 서버 연동을 확장하는 작업이었다면, 이번엔 성격이 다른 새 화면입니다.
지금까지의 모바일 폰 화면(최대 430px 폭)과 별개로, **PC 화면에서 사업장 전체를 한눈에
보는 관리자용 웹 대시보드**를 처음부터 만들었습니다. 같은 서버·같은 계정을 그대로 씁니다.

- 14개 모듈 등록 현황을 카드로, CAPA/PTW는 목록+상태전환까지 처리 가능한 별도 화면으로
- 진행 중인 CAPA·승인 대기 PTW를 상단에 모아 보여주는 긴급 처리 스트립
- **v1.1**: CAPA/PTW를 제외한 나머지 11개 모듈도 카드나 목록을 클릭하면 실제 데이터
  테이블을 볼 수 있습니다(처음엔 건수만 보여주고 상세보기가 없었는데, 이어서 채웠습니다).
  모듈마다 어떤 컬럼을 보여줄지는 `MODULE_COLUMNS` 설정 하나로 관리됩니다 — 서버의
  `simple-crud-factory.js`와 같은 설계 철학입니다.
- 로그인부터 상태전환, 11개 모듈 상세뷰까지 실제 서버에 대해 jsdom으로 검증 완료(재현성
  확인 포함), 검증 스크립트도 함께 제공(`admin-dashboard.zip` 안의 `test/`)

**아직 하지 않은 것**: 상세 목록의 검색·필터·정렬, 다중 사업장 전환, 실시간 자동갱신,
사용자·권한 관리 화면. `admin-dashboard.zip`의 README에 정리해뒀습니다.

이 샌드박스엔 실제 브라우저가 없어 **기능 동작은 검증했지만 실제 화면이 보기 좋게
나오는지는 직접 열어 확인이 필요**합니다.

## 19. 경쟁 서비스 비교 및 개선 (v5.15) — 스마플·무사퇴근 대비

사용자 요청으로 유사 서비스인 스마플(대한산업안전협회·LG유플러스 컨소시엄)과 무사퇴근을
직접 조사했습니다. 스마플은 실제 소개서 18페이지 전체를 이미지로 확인했고, 무사퇴근은
프로젝트에 색인된 기능 목록을 확인했습니다.

### 19-1. 비교 결과

**이미 대등하거나 앞서는 부분**: 위험성평가·CAPA·PTW(승인워크플로우)·아차사고·TBM·교육·
MSDS·PPE·법정선임·법정회의점검·협력업체 13개 모듈의 서버 연동 + 관제센터. CAPA/PTW의
서버측 상태전이 강제 수준은 두 경쟁사 소개 자료에서 이 정도로 구체적으로 설명된 부분은
확인하지 못했습니다.

**진짜 빠져 있던 것 (우선순위순)**:
1. **중대재해처벌법 대응 체크리스트** — 스마플은 "국내 최초 중대재해처벌법 대응 솔루션"을
   대표 마케팅 포인트로 내세우고, 무사퇴근도 별도 카테고리로 분리. 경영책임자 형사처벌과
   직결되어 두 회사 모두 핵심 세일즈 포인트로 사용. **→ 사실은 모바일 앱에 85개 항목으로
   이미 구현되어 있었고, 서버 연동만 빠져 있었습니다. 처음엔 이걸 모르고 12개짜리를 새로
   만들었다가 정정했습니다 (19-2절에 과정 전체 기록)**
2. 안전점검(체크리스트Tool, 작업별 맞춤 점검보고서) 모듈 — 아직 미구현
3. ~~근골격계 유해요인조사·작업환경측정·직무스트레스평가~~ — 19-2절 정정 과정에서 확인한
   결과, 이것도 85개 항목 체크리스트(44~55번, 67번, 53번)에 이미 포함되어 있었습니다.
   다만 "체크리스트에 있다"는 것과 "그 조사를 실제로 기록하는 전용 화면이 있다"는 것은
   다른 문제입니다 — 위험성평가처럼 결과를 구조화해서 기록하는 화면은 여전히 없습니다.
4. 도급업체 정량 안전보건수준평가, 공정/설비 마스터데이터, E-SOP 문서관리 — 있으면
   좋지만 설계 결정이 더 필요한 항목들

**따라할 필요 없다고 판단한 것**: 데이터센터의 재해사례집·법령정보(실제 협회의 축적된
콘텐츠라 저희가 흉내내면 부정확한 내용을 만들 위험), 온라인 교육과정 판매(결제·LMS 인프라
필요), 디지털트윈 모니터링, 이커머스 안전스토어 — 전부 별도의 실제 사업 기반이 필요해
이번 범위에서 제외했습니다.

### 19-2. 중대재해처벌법 대응 — 처음에 잘못 만들었다가 바로잡은 과정

**처음에 한 것**: 법제처 원문(중대재해처벌법 시행령 제4조 9개+제5조 3개 = 12개 항목,
2025.10.1 시행 기준)을 검색해서 확인하고, 반기(period)별로 추적하는 별도 체크리스트를
서버에 새로 만들었습니다. 형사처벌과 직결되는 내용이라 법적 근거는 제대로 확인했습니다.

**문제**: 이걸 만들기 전에 **모바일 앱을 먼저 확인하지 않았습니다.** 실제로는 모바일 앱에
이미 `tab-checklist`("산안법 & 중처법 85개 핵심 법규 DB")가 있었고, 그 안에 산업안전보건법
57개 + 안전보건규칙 16개 + **중대재해처벌법 12개** 항목이 조항 번호·과태료/벌금/징역 수준까지
전부 갖춰져 있었습니다. 심지어 제가 별도 항목으로 다시 만들려던 것(근골격계 유해요인조사,
작업환경측정, 직무스트레스평가)도 이미 44~55번, 67번, 53번 항목으로 다 들어있었습니다.
결과적으로 **더 부실한 12개짜리를 서버에 새로 만들어 기존의 더 완전한 85개짜리와 중복시킨
것**입니다 — "기존 코드를 먼저 이해한다"는 원칙을 스스로 어긴 사례라 정확히 기록해둡니다.

**바로잡은 것**:
- 처음 만들었던 `compliance_checks` 테이블·라우트·반기 개념을 전부 제거했습니다.
- 모바일 앱의 실제 85개 항목 원본 데이터(조항·제목·설명·처벌규정)를 그대로 추출해
  `src/legal-checklist-data.js`로 옮기고, `legal_checklist_items` 테이블로 교체했습니다.
  수동으로 옮겨적지 않고 정규식으로 프로그램 추출해 오탈자 위험을 없앴습니다.
- 반기 스냅샷 대신, 모바일 앱과 동일하게 **항목당 하나의 checked/note 상태**만 유지하고,
  변경 이력은 이미 있는 `audit_logs`(행위자·시각 기록)에 맡기는 쪽으로 단순화했습니다 —
  법이 요구하는 "언제 무엇을 이행했는지 기록"은 반기 버킷을 억지로 만들지 않아도
  실시간 감사로그로 충분히 달성됩니다.
- **모바일 앱의 기존 체크리스트에 서버 동기화를 추가**했습니다. 체크박스를 누르면
  `item_no`(1~85) 기준으로 서버의 해당 항목을 찾아 반영하고(`LegalChecklistSync`), 다른
  사용자가 서버·관제센터에서 바꾼 내용은 "☁️ 서버와 동기화" 버튼으로 가져올 수 있습니다.
  이 체크리스트는 다른 모듈(위험성평가 등)과 달리 "사업장당 하나의 공유 목록"이라, 로컬/
  서버를 분리해서 보여주지 않고 서버 값을 신뢰하는 pull 방식을 택했습니다.
- 관제센터도 반기 선택 UI를 없애고 모바일과 동일한 검색·미이행 필터 UX로 다시 만들었습니다.

**권한**: `safety_manager` 이상만 `/compliance` 접근 가능(근로자 403) — 그대로 유지했습니다.

**검증**: 서버 API(85개 자동시드, 멱등성, 체크+메모 저장), 관제센터(85개 카드 렌더링,
검색·필터, 체크 토글), 모바일 앱(체크 토글 → 서버 반영, 서버 변경사항 → pull로 로컬 반영)
까지 전부 재검증했습니다. `frontend-tests`(37건)·`admin-dashboard`(11건) 두 테스트 스위트
모두 전체 재실행해서 통과 확인했습니다.

**⚠️ 법률자문이 아닙니다.** 조건부 조항(예: 전담조직 관련 항목)이 있고 법이 개정될 수
있습니다. 실제 사용 전 법률 전문가·시행령 원문 확인을 권합니다.
